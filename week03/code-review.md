本轮目标是在保持原有函数调用方式、返回字段和成功时命令行输出格式的前提下，明确只支持实际格式为 PNG 或 JPEG 的图片。真实但不受支持的图片格式应产生清晰错误，不能被当作成功结果输出。

本轮不增加 PDF、OCR、批量处理或网络功能，也不修改 Week 2 的模型推理代码。

## 2. 改动前的证据

原有工具可以读取仓库中的 PNG 样例，输出路径、宽度、高度和格式四行信息。原有三个 pytest 测试通过。

```text

```

两个失败说明：

1. 真实 BMP 图片没有触发预期的“不支持”错误。
2. BMP 命令行输入的退出码为 `0`，还输出了宽度、高度和 `format: BMP`。

该次完整输出保存于 `week03/test-before-fix.txt`。当时运行的是七项测试；另外两项扩展名与实际内容不一致的测试是在此后补充的，不能把它们写成改动前已运行的测试。

## 3. 实现改动审查

实际补丁在 `Image.open(path)` 之后读取 `image.format`，仅允许 `PNG` 和 `JPEG`。如果识别出的真实格式不在允许集合中，则抛出错误信息包含“不支持”的 `ValueError`。

审查结论：

| 项目 | 审查结果 |
|---|---|
| 格式判断依据 | 使用 Pillow 识别出的实际 `image.format`，不是文件扩展名。 |
| 支持范围 | 允许 PNG 和 JPEG；其他已识别格式进入“不支持”错误路径。 |
| 成功返回值 | 保留 `file`、`width`、`height`、`format` 四个字段。 |
| 成功时 CLI 输出 | 仍在函数成功返回后输出原有四行信息。 |
| 不支持格式的错误 | 抛出包含“不支持”的 `ValueError`，由现有 CLI 错误入口处理。 |
| 非图片文件的错误 | 保留“无法识别该图片”的现有处理。 |
| 修改范围 | 可见实现 diff 只涉及 `week01/src/image_info.py` 中的格式判断和格式返回值。 |

新增的“不支持格式”异常是 `ValueError`。现有的 `except (UnidentifiedImageError, OSError)` 不会捕获这个由程序主动抛出的 `ValueError`，因此不会把“不支持”错误误写成“无法识别”。

`"format": image_format or "unknown"` 中的后备值是从原返回结构沿用的写法。在目前的格式白名单下，能执行到成功返回的格式只能是 PNG 或 JPEG，后备值不会成为正常成功结果。这不影响本轮验收。

## 5. 正确性与边界

本次最重要的边界是“文件名不等于实际格式”。测试使用 Pillow 明确生成实际内容为 BMP、文件名却以 `.png` 结尾的文件。该测试在修复后通过，说明最终行为符合基于真实格式判断的任务要求。

现有工具只读取单个本地文件的图片信息。它没有调用 `image.load()` 对整张图片的像素内容进行完整解码，因此本轮测试不能证明它能发现所有类型的截断或损坏图片。这属于后续任务，不扩大本次修改范围。

文件不存在、输入路径不是普通文件、文件无法识别等分支基本沿用原实现。对于某些发生在 `try` 范围内的系统读取错误，现有 `except OSError` 可能将其转成“无法识别”；本轮没有声称完善所有文件系统错误的分类。

## 6. 安全、数据与依赖检查

- 测试图片由 Pillow 在 pytest 的临时目录中生成；本轮没有使用私人图片或真实用户数据。
- 本轮实现没有新增网络请求、命令执行、密钥读取或文件写入功能。
- 测试中的命令行调用使用 `subprocess.run()` 的参数列表和 `sys.executable`，没有把图片路径拼接成 shell 命令。
- 本轮没有新增第三方依赖；继续使用项目已有的 Pillow 和 pytest。
- 已查看实现文件的 Git diff；`git diff --check` 没有输出格式错误。

本轮针对的是受控的本地学习样例。当前工具没有设置图片文件大小或解码资源上限，因此不把它宣称为可直接处理任意不可信图片的生产级服务。
